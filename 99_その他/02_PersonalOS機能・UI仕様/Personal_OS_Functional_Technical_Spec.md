## 2. アプリの目的と基本方針

個人のタスクと複数のプロジェクトを管理し、今日の着手・完了・進捗確認を軽い操作で行う。白基調・コンパクトなRPG風デザインは12画面一覧を土台とする。機能はToDo中心とし、新規Androidアプリとして作る。

Task登録数・今日のTask件数に商品上の上限を設けない。今日のメインは最大1件。XP・レベルの表示は設定で選べる。職業・称号・宝箱・ペット・装備・素材・合成・拠点・ショップ・通貨・戦闘は入れない。


## 3. 初期版に含めるもの

- 今日・プロジェクト・タスクの3タブ。
- Taskの追加・編集・検索・分類・予定日・期限・状態変更。
- 名前だけで登録できる入力。Projectに属さない単発Taskも可。
- 今日のメイン設定・解除・置換。通常一覧と重複表示しない。
- 候補・未着手・実行中・待ち・完了・中止の6状態。
- 完了、押し間違いのUndo、後日の再開。
- Project作成・編集、配下Task、進捗、確認付き完成・再開。
- 中止・保管と通常一覧への復帰。完全削除・ゴミ箱は初期版対象外。
- 難易度別Task XP、規模別Project完成XP、従来レベル式。
- 全画面共通の文字・密度・XP・演出・左右配置設定。
- 手動バックアップの書き出しと、確認付き全体復元。
- スマホ単体のローカル保存。

## 6. 分類とProject所属

Task分類は所属時にProject分類を初期値として継承し、その後Taskごとに変更可能。

Project分類を変更した場合は、Task側で個別変更していないものだけ追従する。個別変更したものは維持する。単発Taskは分類を直接指定できる。

設計事項：分類値が同じかどうかだけでは個別変更の有無を判定できないため、継承／個別指定の情報を保持する。TaskのProject移動・所属解除時の分類保持規則を詳細設計で明示する。継承に戻すUIは設計提案として検討する。


## 7. 状態・進捗

| 内部名 | 表示上の意味 | Project進捗 |
|---|---|---|
| BACKLOG | 候補・いつか | 除外 |
| TODO | 未着手 | 分母 |
| DOING | 実行中 | 分母 |
| BLOCKED | 待ち | 分母 |
| DONE | 完了 | 分子・分母 |
| CANCELLED | 中止 | 除外 |

対象件数＝TODO＋DOING＋BLOCKED＋DONE。進捗率＝DONE÷対象件数×100。対象0件は0%。表示は四捨五入の継承案。準備完了は丸め後の100%ではなく、対象1件以上かつ全件DONEで判定する。

保管は通常表示から外す扱いであり、7つ目の作業状態と混ぜない設計案。保管しただけで作業を完了させたりXPを付与しない。保管と進捗対象の関係・復帰操作は詳細設計に記載する。


## 8. 今日・Main・日付

Main指定は今日だけ。未来日のTask予定登録は可能だが、未来のMain予約は入れない。Mainなしでも利用できる。別のTaskをMainにすると前のMainは通常Taskとして残る。

前日までの未完了は別枠で保持し、本人が必要なものだけ今日へ移す。自動繰越しない。対象は予定日が今日より前で、状態がTODO／DOING／BLOCKEDのTask。予定なし・未来・DONE・CANCELLED・BACKLOGを混ぜない。

今日への移動でTask ID・期限・状態・XP履歴を変えない。過去のMainと今日のMainが競合する場合は置換／通常Taskとして移動／キャンセルを設計する。件数上限による満員処理は不要。

基準日は端末ローカル日付。初回、前面復帰、開いたままの日付変更時に表示を更新する。日付だけの予定・期限と、記録の時刻を分離する。


## 9. Project完成と再開

残Taskがあっても、件数と進捗を表示して本人が確認すれば完成できる。残Taskを自動DONEへ変更しない。進捗100%になっても自動でProjectを完成させない。

完成済みProjectへTaskを追加する場合、または配下の完了Taskを未完了へ戻す場合は「Projectを再開しますか？」と確認してから処理する。拒否なら該当の変更を行わない。

設計事項：既存Taskの移動、キャンセル解除など未指定の経路でも同じ整合原則を適用する案。完成操作のUndo、0件Projectの完成、完成イベント履歴の持ち方は詳細設計で明示する。


## 10. XP・レベル

### 確定した計算と設定

| 対象 | 区分 | 初回XP |
|---|---|---:|
| Task | EASY | 20 |
| Task | NORMAL | 50 |
| Task | HARD | 100 |
| Project完成 | SMALL | 100 |
| Project完成 | MEDIUM | 300 |
| Project完成 | LARGE | 700 |

初期表示はXP・レベルともON。設定で非表示にしても内部記録は継続する。再表示したときに過去分も反映。非表示切替で付与イベントを削除・再作成しない。

従来のレベル式：現在LvをLとし、次Lv必要XP＝220＋65L＋11L²を10 XP単位に四捨五入。必要量はLvごとの値であり累積閾値ではない。

| 遷移 | 必要XP |
|---|---:|
| Lv1→2 | 300 |
| Lv2→3 | 390 |
| Lv3→4 | 510 |
| Lv4→5 | 660 |

初回Lv1・0 XPの従来方針を継承。合計770 XPならLv3・Lv内80/510 XP。過去の個人実績やデモ値を初期投入しない。

### 保存原則と再付与

付与量はイベントとして保存し、累積XP・レベルは派生計算する構成案。付与時点の額を保存し、後で難易度・規模を変えても過去額を再計算しない。TaskやProjectの通常再開・再完了では、同一対象への初回報酬を再付与しない従来ルールを継承する。

難易度・Project規模は手動選択を基本とする。新規時の初期値NORMAL／MEDIUMは継承候補。入力を軽くするため名前だけの登録を維持する。


## 11. 押し間違いのUndoと、後日の再開

| 操作 | Task状態 | XP |
|---|---|---|
| 直後の「元に戻す」 | 完了前の状態へ復元 | その操作で付与したXPを取り消す |
| 後日の「再開」 | TODOへ戻す | 獲得XPを維持。再完了で再付与しない |

重要：以前にXP獲得済みのTaskを再完了した操作には新規付与がない。この操作をUndoしても、過去の初回XPまで消してはいけない。取り消すのは対象操作の差分だけ。

設計事項：Undoの提供時間・画面遷移後の有効性・別操作後の可否、XPイベントの取消表現、二重Undo防止、Project状態の復元を詳細設計で明示する。Undo後の実完了では取消済み報酬の再付与が可能な方式とし、単純な一意制約の削除や二重登録で処理しない。


## 13. 手動バックアップ・全体復元

初期版に手動の書き出し・読み込みを入れる。読込みは統合ではなく全体復元。復元内容を確認し、現在データを退避したうえで置換する。無確認で消去しない。

設計案：

1. ファイルを選び、版・形式・参照・XP等の整合性を検証する。
2. 復元される件数・日時などを表示する。
3. 現在のデータを退避する。退避が失敗した場合は置換を進めない案。
4. 本人が確認したら全体を置換する。
5. 途中失敗で半端なデータが残らないよう、DB・設定を含む復旧方式を設計する。

含める実体、ファイル形式、互換性、破損ファイルの拒否、最大サイズ、退避先・復元失敗時の復旧は詳細設計事項。バックアップ対象からXP実績を落として再付与を招かない。署名鍵や開発用秘密情報はバックアップへ入れない。

# 実装基準案（確定事項と区別）

## C. 入力と初期値の基準案

| 項目 | 基準案 |
|---|---|
| Task | title必須・空白だけ不可、status TODO、difficulty NORMAL、Projectなし、分類General |
| 予定日 | 今日画面からの追加は今日。全Task画面からは未設定。Project詳細からも未設定 |
| Project | title必須、status PLANNING、size MEDIUM、分類General、期限任意 |
| 文字・密度 | 本文16sp、標準密度、タイトル2行まで、詳細で全文 |
| 本文上限 | Task名150、Project名100、メモ10,000 Unicodeコードポイントを案とする。超過はエラー、無断切捨てなし |
| 順序 | 初期はユーザー順。自動並替えする場合は完了直後の押し間違いを避ける |
| Undo | 直近のTask完了1操作だけ、10秒の案。画面移動は可。他の永続変更・アプリ終了で無効 |

Undo有効中でも通常の「再開」を選べる。現在値と操作時の対象revisionが一致する場合だけUndoし、過去の別操作を巻き戻さない。アクセシビリティ設定によって時間を延長できる設計を検討する。10秒はユーザー決定ではなく見本・実装基準案。


## D. データ設計の基準案

| 実体 | キー・項目 | 制約 |
|---|---|---|
| Category | id, name, sortOrder, revision, timestamps | 初回General。IDで参照 |
| Project | id, title, goal, description, categoryId, lifecycle, size, dueDate, archived, completedAt, revision | lifecycleは計画・進行・休止・完成。保管フラグを別保持する案 |
| Task | id, title, notes, projectId?, categoryMode, categoryId?, status, difficulty, plannedDate?, dueDate?, archived, sortOrder, completedAt, revision | categoryModeはINHERIT／EXPLICIT。所属なしはEXPLICIT |
| MainAssignment | localDate, taskId | 1日1件。UIは今日だけ指定可。参照Taskの予定日と整合 |
| XpAward | sourceType, sourceId, amount, ruleVersion, grantOperationId, active | sourceType＋sourceIdを一意。取消済みを残し、次の真の完了で再有効化可能 |
| Operation | id, type, targetId, beforeState, afterRevision, awardDelta, occurredAt, undoOf? | 冪等キー。Undoが取り消す付与だけを特定 |
| DisplaySettings | schemaVersion, showXp, textSize, density, titleLines, hand, motion, sound, haptics | DataStore。共通設定のみ |

Category追従は単なる値一致で判定しない。INHERITは参照先の分類を読み、EXPLICITはTask側を読む。Project移動時はINHERITなら新所属へ追従、EXPLICITなら維持する案。所属を外すときはその時点の分類をEXPLICITとして固定する案。

保管は進捗を変えない案。保管済みTaskも状態が対象なら分母へ含める。分母から外す意図なら中止を使う。これを詳細・保管操作の説明に示す。Projectの保管は配下Taskの状態・保管フラグを勝手に変更しない案。

中止・保管したMainは当日の強調から外す案。候補・中止からMainを指定するときは、確認後TODO＋今日へ変更する案。DONEのMainは当日完了表示を維持する。


## E. 状態更新の責務

全ての入口（チェック、詳細、編集フォーム）を同じRepository処理へ流す。編集フォームでDONEへ変更してもXPを回避・重複させない。DONE→別状態も再開／Undoのルールを適用する。

| 操作 | 不可分に扱う更新 |
|---|---|
| Task完了 | 前状態保存、DONE、completedAt、初回XpAward、Operation |
| Undo | revision照合、前状態復元、そのOperationが新規付与したXpAwardのみ取消、Undo記録 |
| 後日の再開 | 完成Projectなら先に確認、Project再開、Task TODO、completedAtクリア。XpAwardは不変 |
| Main置換 | 日付とTask状態を検証、旧参照解除、新参照設定 |
| Project完成 | 必要なら残件数確認、COMPLETED、completedAt、初回規模別Award、Operation |
| 完成後の追加・移動 | 再開確認、親Project再開、Task追加／移動 |
| Project分類編集 | Project分類更新。明示Task分類を上書きしない |

XpAwardがactive=falseへ変わるのは厳密Undoだけ。通常再開・難易度変更・保管・中止・表示OFFは初回付与を失わせない。Undoで過去Awardを一括削除しない。Project完成の厳密Undoは今回の確認で明示されていないため、初期案では再開操作のみとし、TaskのUndoへ自動拡張しない。

0件Projectの完成は旧条件に明確な指定がない。実装基準案は「対象Taskがないことを警告して、本人確認後に完成可能」。進捗0%・準備完了falseは維持。Task件数で自動完成しない。


## F. バックアップ設計の基準案

JSON等の形式はCodexが版管理を含めて確定し、仕様へ記録する。format、formatVersion、exportedAt、appVersion、categories、projects、tasks、mainAssignments、xpAwards、必要な操作実績、displaySettingsを含める案。Undoの一時トークンは復元しない。

読み込み前にファイル上限、形式、版、ID重複、参照、enum、日付、整数、XPの非負と範囲、Main一意、分類モードを検証する。不正時は現在データを変えない。UIには件数・バックアップ日時・全体置換であることを示す。

本番案：現状の復旧用スナップショットをアプリ内へ確実に退避→検証済みデータを準備→復元中状態を永続記録→Room内更新をトランザクション→設定適用→完了マーカー。途中終了時に復旧または完了できる回復処理を設け、半端なDB＋設定で通常画面を開かない。RoomとDataStoreを単一トランザクションにできると誤認しない。ユーザーが選ぶ外部退避先への出力も別途用意する。

HTMLデモはlocalStorageの1レコード置換で見本を示す。Androidの複数保存先・SAF・署名更新・プロセス終了の保証を検証したものではない。
