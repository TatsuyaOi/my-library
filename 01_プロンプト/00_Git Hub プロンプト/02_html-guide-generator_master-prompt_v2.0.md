## 1. 実行モード

### GUIDE_FROM_SOURCE
既存Markdownを正本として読み取り、**原本Markdownを変更せず**HTML説明書だけを新規生成します。

原本Markdownが添付されている場合の標準モードです。

### CREATE_PAIR
原本が存在しない新規依頼から、Markdown原本とHTML説明書を同時生成します。

### UPDATE_GUIDE
既存Markdownと既存HTMLを照合し、原本を変更せずHTMLだけを更新します。

### AUDIT
原本とHTMLの内容・Version・リンク・相対パス・スマホ表示・生成元hashを監査します。修正依頼がある場合だけHTMLを修正します。

### AUTO
入力状況から上記を自動判定します。

## 2. モード別の必須成果物

### GUIDE_FROM_SOURCE

- `{id}_guide.html`
- 原本Markdownは変更しない
- 必要なら生成レポートを短く示す

### CREATE_PAIR

- prompt資料：`{id}_prompt.md` + `{id}_guide.html`
- その他資料：`{id}_source.md` + `{id}_guide.html`

### UPDATE_GUIDE

- 更新した `{id}_guide.html`
- 原本を変更していないことの確認

### AUDIT

- 診断結果
- 修正版はユーザーが修正を求めた場合のみ

ファイル生成能力がある場合は、必ず実体のあるダウンロード可能ファイルとして生成してください。

## 4. 内容整理の基本方針

- 私が指定した目的・条件・入力情報を漏れなく反映する
- 単なる文章化ではなく、情報を分類・整理・構造化する
- 不要な重複を減らす
- 同じ階層の項目は粒度をそろえる
- 必要に応じて見出し、箇条書き、番号付きリスト、表、比較表、注記を使う
- 長文でも見出しだけで全体像を把握できる構造にする
- 重要情報を勝手に省略しない
- 事実、入力情報、推論、提案を混同しない
- 不明点や推測は明示する
- 読者が理解・判断・再利用しやすい順番に整理する

## 5. Markdown原本の作成・保持条件

この節は `CREATE_PAIR` モード、またはユーザーが原本Markdownの新規作成を明示した場合に適用します。`GUIDE_FROM_SOURCE` / `UPDATE_GUIDE` では、添付された原本Markdownを読み取り専用の正本として扱い、内容・改行・Version・ファイル名を勝手に書き換えないでください。

新規Markdown版は、**編集・保存・再利用・AIへの再入力**に適した形式にしてください。

### 必須条件

- 拡張子：`.md`
- 文字コード：UTF-8
- 標準的なMarkdown記法を使用
- 文書冒頭にタイトルを置く
- 見出し階層を適切に設定する
- 原則として `# → ## → ### → ####` の順序を守る
- 比較情報にはMarkdown表を活用する
- 必要に応じてコードブロックを使う
- 過剰な装飾を避ける
- AIが再読込しても構造を理解しやすい形式にする

---

## 6. HTML版の作成条件

HTML版は、**ブラウザで直接開いて完成資料として読める品質**にしてください。

### 必須条件

- 拡張子：`.html`
- 文字コード：UTF-8
- `<!DOCTYPE html>` を含める
- `<meta charset="UTF-8">` を設定する
- `<meta name="viewport">` を設定する
- 単体で開ける自己完結型HTMLにする
- 原則として外部CSS・外部JavaScriptに依存しない
- CSSはHTML内部の `<style>` に記述する
- PC・スマートフォンの両方で読みやすいレスポンシブ設計にする
- 見出し、本文、表、注記、重要ポイントを視覚的に区別する
- 表が狭い画面では横スクロールできるようにする
- 長い資料では目次とアンカーリンクを付ける
- 印刷・PDF化でも大きく崩れない構造にする
- 派手さより可読性・視認性を優先する

## 7. HTML版の情報表現・視覚化の自動選択

HTML版では、入力文章をそのまま縦に並べるだけの資料にしないでください。

各情報を分析し、以下の表現手段から **最も短時間で理解しやすい形式** を自動選択してください。

### 使用候補

- 通常文章
- 箇条書き
- 強調ボックス
- 要点カード
- 比較表
- データ表
- 棒グラフ
- 折れ線グラフ
- 散布図
- 円・構成比グラフ（適切な場合のみ）
- SVG模式図
- フロー図
- 因果関係図
- 層構成図
- タイムライン
- 画像
- アイコン
- タブ
- 折りたたみ（details / summary）
- ツールチップ・補足
- 検索・フィルター
- チェックボックス
- スライダーなどの簡易インタラクション
- 地図・ルート表示（利用環境と必要性が合う場合）
- その他、その情報の理解を明確に改善する表現

### 最重要原則

**視覚要素は装飾のためではなく、理解速度・比較性・因果関係・構造把握・意思決定を改善する場合にのみ使用してください。**

「使える機能をすべて使う」のではなく、情報ごとに適切なものだけを選択してください。

原則として、1つの情報単位には1つの主要表現を選び、複数表現を併用する場合は役割が重複しないようにしてください。

## 9. HTML生成前の内部設計フロー

HTMLを直接書き始める前に、内部で以下の順序で設計してください。

1. 入力情報を事実・推論・提案・参考情報に分類する
2. 情報をテーマごとに整理し、重複を統合する
3. 各情報の重要度を A / B / C などで内部評価する
4. 各情報について「文章で十分か」「視覚化すると理解が改善するか」を判定する
5. 視覚化する情報には、表・グラフ・模式図・画像・タイムライン等の最適な形式を割り当てる
6. 最初の画面で何を見せるかを決める
7. PCとスマートフォンの両方で崩れにくいレイアウトを設計する
8. 詳細情報・生データ・補足の収納場所を決める
9. その後にHTMLを実装する

設計過程そのものをユーザーに長々と出力する必要はありません。最終成果物の品質に反映してください。

## 10. 情報の4階層設計

長いHTMLでは、読者が必要な深さまで段階的に読めるようにしてください。

### LEVEL 1：5秒で理解
- タイトル
- 結論
- 最重要ポイント
- 代表的な図・カード・数値

### LEVEL 2：1分で理解
- 比較表
- 代表グラフ
- 模式図
- タイムライン
- 要因や判断材料の要約

### LEVEL 3：詳しく理解
- 詳細説明
- 考察
- 根拠
- 条件差
- メカニズム
- 代替案

### LEVEL 4：確認・再利用
- 生データ
- 詳細表
- 補足
- 参考情報
- 前提条件
- 注記

重要情報をLEVEL 4に隠しすぎないでください。結論に必要な情報はLEVEL 1〜2で把握できる構成にしてください。

## 11. 視覚要素の使用量と過剰装飾の防止

以下は標準的な目安です。内容上必要な場合は増減して構いません。

- メインビジュアル：1〜2個
- グラフ：原則として1テーマにつき1グラフ
- 比較表：1〜3個程度
- 模式図：1〜3個程度
- 強調カード：3〜6個程度
- タブ：独立カテゴリが複数あり、切り替えが理解を助ける場合のみ
- 折りたたみ：詳細情報・補足・生データ向け
- アニメーション：原則使用しない。必要でも控えめにする
- アイコン：情報識別の補助としてのみ使用する

以下を避けてください。

- 同じ内容を表とグラフで無意味に重複表示する
- 意味のないカード化
- すべての節を色分けする
- 過度なグラデーション
- 読みにくい小さい文字
- 横幅を使いすぎるレイアウト
- スマートフォンで操作しにくい複雑なUI
- 装飾目的だけのアニメーション
- 実データがないのに精密なデータ可視化を作る

## 12. グラフ・模式図・画像の使い分け

### グラフ
数値データが存在し、比較・傾向・分布・関係性を視覚化した方が理解しやすい場合に使用してください。

- 時系列 → 折れ線
- カテゴリ比較 → 棒
- 相関 → 散布図
- 構成比 → 構成比表現。ただし項目が多い場合は棒グラフ等を優先
- 複数指標 → 読みやすさを優先し、無理に1グラフへ詰め込まない

根拠となる数値がない場合は、架空のグラフを作成しないでください。

### SVG模式図
以下のような構造説明に積極的に使用してください。

- 層構成
- 装置構成
- メカニズム
- 原因と結果
- 材料間の関係
- 工程フロー
- システム構成
- 概念整理

模式図は実測画像と誤認されないよう、必要に応じて「模式図」「概念図」と明記してください。

### 画像
画像が理解を実質的に改善する場合に使用してください。

- 実物写真
- 観光地
- 製品
- 外観
- 実験画像
- 代表的な視覚イメージ

入力資料に画像がある場合は、その意味を踏まえて適切な位置へ配置してください。

実画像が存在しない場合に、架空の実験写真・証拠画像・測定画像を捏造しないでください。その場合はSVG模式図や概念図を使用してください。

JavaScriptによるインタラクションは、閲覧性を改善する場合に限定してください。

### 使用を推奨
- 長い詳細説明の折りたたみ

- 学習用の「問題 → 解答表示」

### 原則不要

- 過度なホバー依存
- スマートフォンで扱いにくい複雑操作

重要情報は、JavaScriptが動かない状況でも可能な限り読めるようにしてください。

## 14. 自己完結型HTMLの実装優先順位

可能な限り、1つのHTMLファイルだけで閲覧できる構成を優先してください。

優先順位：

1. CSSは `<style>` に内包
2. JavaScriptは `<script>` に内包
3. 模式図はインラインSVG
4. 小規模アイコンはSVGまたはCSS
5. 画像を埋め込む必要がある場合は、環境が許せばData URI / Base64等を検討
6. 外部ライブラリは、本当に必要な場合だけ使用
7. CDN依存は可能な限り避ける

Chart.js、Plotly等を使う場合も、外部依存による利点と自己完結性を比較し、目的に適した方法を選んでください。

ネット接続が必要な地図・動画・Web埋め込みなどを使用する場合は、オフラインでは利用できないことが分かるようにしてください。

## 16. Markdown原本とHTML説明書の整合性

両形式は、表現方法が異なっても **情報量・意味・結論を実質的に一致** させてください。

- Markdown原本：編集・保存・AI再利用向けの正本
- HTML説明書：人間が閲覧する派生物

HTMLでは、Markdownの文章をそのまま縦に並べず、必要に応じて表・グラフ・模式図・カード等に再構成できます。

ただし、次を守ってください。

- HTMLだけに新しい事実を追加しない
- 原本にある重要情報を省略しない
- 原本VersionをHTML上で正確に表示する
- 原本のタイトルとitem IDを保持する
- 原本のSHA-256を計算できる場合、HTML生成時の値を記録する
- 現在の原本SHA-256と生成時SHA-256が異なる場合、古いHTMLを最新と扱わない
- hashを計算できない場合は、計算したふりをしない

# 19. GitHub Library用HTMLの共通機能

Library Contract 2.0を使う場合、HTMLへ次を実装してください。

## 識別情報

- item ID
- 正式タイトル
- 原本Version
- 原本ファイル名
- 生成元SHA-256（計算可能な場合）
- HTML生成プロンプトIDとVersion

HTMLの画面上へすべて大きく表示する必要はありません。必要に応じてフッター、`meta` 要素、控えめな情報欄へ配置してください。

## ナビゲーション

入力で実在確認できた場合のみ：

- 「ライブラリへ戻る」
- 「原本MDを開く」
- 「原本をコピー」
- 関連資料へのリンク

不明な相対パスを推測して壊れたリンクを作らないでください。

## コピー機能

原本コピー機能は、原則として相対パスのMarkdownを `fetch` して取得します。

- `file://` 直開き等でfetchできない場合は、原本を開くリンクと分かりやすい案内を表示
- 原本全文を巨大なJavaScript文字列へ二重埋め込みしない
- Clipboard APIが使えない環境でもHTML本文の閲覧を壊さない
- 取得した文字列をHTMLとして解釈しない

## GitHub Pages互換

- 相対パスを使用
- `C:\\...`、`file:///...` を含めない
- `/assets/...` 等のドメインルート絶対パスへ安易に依存しない
- 大文字小文字を実ファイルと一致
- GitHubユーザー名・リポジトリ名をハードコードしない
- ローカル確認は可能ならHTTPサーバー経由で行う

## 最重要指示の再確認

- 原本Markdownが添付されている場合は、原則 `GUIDE_FROM_SOURCE` として原本を変更せず、HTML説明書を実生成してください。
- 新規資料をゼロから作る場合だけ、必要に応じてMarkdown原本とHTML説明書を同時生成してください。
- コードや本文をチャットへ表示しただけで完了扱いにしないでください。
- 実ファイルを生成できない場合は、その事実を明示し、作成済みと表現しないでください。
