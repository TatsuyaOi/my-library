# GitHub Library Prompt Suite 2.1.0 改訂・検証レポート

作業日：2026年9月5日／Library Contract：2.0／マスタープロンプトの正規フォルダ：`プロンプト一覧/`

## 1. 結論と範囲

00〜08の全面ファイルを改訂し、09 Prompt Quality Auditorを新設しました。既存の原本保持、スマホ優先、視覚表現の自動選択、固定デザイン、公開制御、派生物hash、PWA、公開監査という専門機能は維持しています。
管理用のAGENTS、Issue/PR、Suite同期・検証、評価ケース、Libraryの基礎実装、任意のPages Workflowを補いました。

完成物の範囲は「改訂済みの指示書一式＋ローカル管理・検証ツール」です。GitHubの既存リポジトリ変更、Projects作成、push、Pagesへの公開、既存HTML/PWAの移行は実行していません。
独立した実モデルによるA/B比較はNOT_RUNです。ローカルの構造検証PASSをプロンプトの実出力性能PASSへ流用しません。
最新の実行結果はルート `VALIDATION_REPORT.md` と `reports/local/` に保存します。

## 3. 改善前の主要問題

実際の03はv2.3でしたが、旧README・Manifest・Validation・CHANGELOGはv2.2まででした。
一方、旧Manifest対象の03以外の10ファイルは、添付のCRLFをLFとして比較した場合に旧hash・bytesが一致しました。これは内容改ざんではなく、実byteと改行の扱いを分けて考えるべき不一致です。
新パッケージではUTF-8・LFを固定し、保存後の実byteをManifestに記録します。既存content原本は移行時に勝手に改行変換しません。

ほかに、04/05のAUDITが修正まで進む指示、未実施検査を警告付きPASSへ混ぜ得る判定、timestampによる非決定性、previewとthumbnailの連鎖鮮度、生成履歴の後付け上書き、公開repoと公開索引の混同を修正・補強しました。

## 4. 3方向の比較と採用

| 方向 | 長所 | 問題 | 採否 |
|---|---|---|---|
| A：LEAN | 文言・版ズレだけ修正し導入しやすい | 自動検出・未実施の判定・回帰管理が不足 | 単独では不採用 |
| B：BALANCED | 原文の機能と構造を保持し、明確な矛盾を最小差分で修正 | 基盤の不足には追加実装が必要 | 本文改訂の中心として採用 |
| C：MAXIMUM | 要件台帳、実検証、Red Team、CIで取りこぼしを減らす | 毎回全工程・全候補全文を強制すると過剰 | 必要な管理・安全策だけ採用 |

採用版はBを中心にCの証拠・回帰・安全境界を統合した1セットです。3本の巨大な改訂案を重複納品するのではなく、違いと採否をここに残しています。これは設計比較であり、モデルA/Bの勝敗ではありません。

## 6. 原文保持と追跡

00〜08の元の非空行4,840行を比較したところ、改訂版内に同じ文字列で存在する原文行は4,785行、改訂対象になった原文行は55行でした。
これは行の存在の検査であり、意味の一致や配置の妥当性を自動証明する数字ではありません。重複行も元の出現単位で数えています。
変更行すべてに理由を付け、`reports/changed-source-lines.md` と完全diffで確認できるようにしました。旧版の専門本文を「既存部分を維持」の一文で省略する方法は使っていません。

重要な原文・追加要件82件を `docs/requirements.json` と `docs/要件追跡表.md` に整理しました。対応先fragmentと評価ケース／単体テストの参照を実検査します。
82件の対応が揃うことを「すべての生成性能が100%保証された」と解釈しません。STATIC_ONLY項目には実動作の試験がまだなく、モデルのMUST遵守は実出力で別確認が必要です。

## 8. Red Teamで発見・修復した問題

| 問題 | 修復 | 確認 |
|---|---|---|
| CI内の再生成で版ズレを隠せる | --writeを変更ブランチに限定、CIは--check | 旧README・改訂MDの負例テスト |
| hashがLF版なのに実byteを検証済みと誤認 | 実bytehashと改行規約を独立検査 | 同期済みhashでもCRLFを拒否 |
| 古いpreview由来のthumbが残る | 全依存の鮮度をたどる | 連鎖鮮度の負例 |
| additionalが鮮度検査を迂回 | 管理派生物の重複指定を拒否 | 迂回する負例を追加 |
| public関連IDや内部レポートの漏えい | 公開IDだけ射影、レポートをsite外に限定 | 公開射影・書込み前拒否の試験 |
| 既存siteを誤って削除 | 所有マーカー・専用出力・一時staging | 未管理site保持、全消失を既定拒否 |
| 監査の不存在を合格にできる | 現在build＋必須EXECUTED PASS＋証拠を要求 | 記録不足・別buildを拒否 |
| コピー部分だけ使うと追加規則が落ちる | 01の27節と03の16-A節をコピー対象内へ配置 | 保存後に節位置を照合 |
| 台帳のテストIDが別のケースを指す | 実ケースと単体テストの内容に対応を修正 | 参照先存在検証、机上内容照合 |

テスト作成中に発見したインデント不正も修正し、再実行しました。テストの期待値を緩めて成功扱いにはしていません。

## 9. 実行検証と未実施を分ける

Suite構造・JSON・YAML・Python構文・hash・版・参照はEXECUTEDです。
Python回帰テストは正常系に加え、公開条件、ID衝突、symlink、stale、余剰ファイル、未所有site保護、リンク、偽PASSなどを実際に試します。
15ケースの仕様照合はSIMULATED、対象モデル・画像・ブラウザへの完全なシナリオ実行はNOT_RUNです。詳細は `reports/scenario-review.md` にあります。

未実施：独立したLLMの同一条件A/B、複数回生成の変動評価、人間の盲検判定、実画像デコード品質、深い404の実ブラウザ遷移、PWA登録／更新／オフライン／取り消し、Android実機、実GitHubの設定・権限・公開結果。
レポート内の単体テスト用画像byte列はsynthetic fixtureであり、生成画像や描画成功の証拠ではありません。

## 10. 納品後の入口

既存リポジトリにはZIPを丸ごと上書きせず、`docs/移行ガイド.md` と `docs/Codex初回指示.md` から差分統合してください。
すでにあるindex・PWA・資料・category・公開設定を変更しないことが初期条件です。
初回はSuite検証と代表プロンプトの評価を行い、公開Workflowは有効化しないまま利用できます。
`site-ui/` と `content/` は既存資料を受け取る入口であり、今回架空の本番サイトを生成したものではありません。
