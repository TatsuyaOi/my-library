# 日常運用ガイド

## 役割を分ける

「プロンプト一覧」は作り方の正本。「content」は作られた個別資料の正本。「site」は公開用生成物。
Suite管理とLibrary公開を分離し、資料を追加するだけでマスタープロンプトのVersionを上げない。

## 一人開発の標準

Issueで目的・非変更範囲・成功条件を書く。Codexは作業ブランチで変更し、検証してPRへまとめる。
mainは採用済み状態とする。ただしBranch保護・必要レビュー数はGitHub設定で別途設定するもので、MDだけでは強制されない。
一人運用で自分以外の承認を必須にすると処理が詰まることがあるため、CI必須と自己チェックを基本にし、レビュー人数は実態に合わせる。

## 改訂の手順

対象Componentの目的・MUST・例外を確認し、変更理由を記録する。
Component Versionは旧版の最後の数値を1つ増やす。例：1.9→1.10。
Suiteの公開区切りは別に管理し、Library Contractはデータ互換が変わるときだけ変更する。
CHANGELOGを更新し、`build_suite_manifest.py --write` でManifestとREADME表を同期する。
`--check` と `validate_suite.py` とunittestを実行してPRへ証拠を添える。

## 2種類の検証

Suite構造検証：ファイル・ID・Version・JSON・Markdown・ハッシュ・参照の整合。
プロンプト性能評価：テスト入力を実際の対象AIへ渡し、出力を同じ基準で評価。
前者のPASSは後者の成功率ではない。15ケースの設計があっても、実行していなければNOT_RUN。
09の構造監査を終えた後、重要な改訂では実出力のペア比較を行う。

## GitHub Actions

`validate-prompt-suite.yml` はpush／PR／手動実行でSuiteを検証する。ネットワーク経由のモデル呼出しは行わない。
`validate-and-deploy.yml` はLibraryを統合した後だけ使う。Repository Variableの初期未設定では公開しない。
公開を有効化する前に、PagesのSource、正式ブランチ、Environment、private資料の扱い、index/404/PWAの実テストを確認する。
ActionsのSHAは公式release→commitで確認した固定点。最新であるとの保証ではない。Dependabotの更新もレビューする。

## Public / Private

meta.jsonのprivateはアプリ側分類。GitHub repoの閲覧制御、Pagesの公開、ブラウザcacheの保存は別レイヤー。
既に公開した情報は非公開化しても保存済みコピーまで消せない。機密資料は最初から公開しない。
シークレットが公開された場合は失効・再発行を優先し、履歴書換えは独立した明示承認の作業にする。

## 段階的に使う

初期はIssue→変更→Suite検証→PRで十分。
ProjectsはTodo／In Progress／Review／Doneの4状態から開始する。詳細設計は `docs/GitHub管理設定.md`。
本番出力が蓄積したら、失敗例を匿名化してevalsへ追加し、開発集合とholdoutを分ける。
